Sandboxed Code Kernels: Closing the Mathematical Reasoning Gap for Compact Open Models

How pairing compact 27B open weights with isolated Python execution environments delivers research-grade math accuracy without fine-tuning.

An open-weight 27B model evaluating 300 research-level problems from TCS-Bench passed only 4.0% of problems when drafting unassisted proofs in a single pass. Even frontier models scaled to hundreds of billions of parameters struggle with subtle invariant shifts and false algebraic confidence when unguided. Deploying those massive proprietary checkpoints also requires expensive cloud compute clusters that remain out of reach for independent researchers. When generative language models tackle formal mathematics without external tools, small syntactic substitutions quickly produce invalid intermediate steps. Standard autoregressive decoding lacks an internal mechanism to test whether an algebraic transformation preserves truth conditions. Because each generated token conditions the next prediction, early errors compound until the entire derivation collapses into plausible nonsense. The resulting performance gap has long fueled the assumption that reliable mathematical deduction requires massive parameter scale. Recent empirical results challenge that assumption by changing how models interact with execution environments.

The Architecture of Programmatic Verification

Instead of training larger models, researchers augment compact weights with dedicated symbolic execution runtimes. This supervisory setup pairs an open-weight language model with a stateful, airgapped Python execution environment. Inside that execution environment, the language model interacts directly with SymPy for symbolic algebra, Z3 for satisfiability modulo theories constraint solving, mpmath for arbitrary-precision arithmetic, and NetworkX for graph analysis. Rather than performing multi-step algebraic manipulation in text space, the model outputs Python code blocks targeting these deterministic libraries. The symbolic libraries evaluate each step, verify invariants, and return concrete output back to the model. By offloading arithmetic and symbolic transformations to specialized software, the model focuses on high-level strategic reasoning rather than error-prone mental math.

Kernel Isolation and Execution Guardrails

Connecting an autoregressive model to a code interpreter introduces operational challenges that demand strict architectural guardrails. A naive shared environment quickly accumulates variable pollution, overwriting variables and introducing stale dependencies across proof iterations. The verification system solves this contamination by splitting execution roles into distinct operational scopes. The solving agent operates in a persistent scratchpad, but the validation auditor runs in a fresh, ephemeral kernel governed by a strict 15-second timeout. This short timeout ensures that infinite recursion or complex constraint queries abort before consuming unnecessary compute.

Numerical precision presents another failure mode when models evaluate non-trivial analytical expressions. Standard IEEE-754 floating-point representations introduce small rounding errors that can invalidate asymptotic bounds or identity checks. Pre-configuring 50 decimal places of precision inside mpmath ensures the agent avoids misleading floating-point artifacts. In addition, models often resort to brute-force search when analytical paths appear difficult. To prevent computational waste, the sandboxed execution kernel sets a loop ceiling of 200,000 iterations via a guarded range function. When a script exceeds 200,000 iterations, the kernel triggers an immediate boundary error. This hard stop compels the model to abandon brute-force searching and derive the exact analytical formula or generating function.

Empirical Validation on Formal Mathematics

The quantitative impact of wrapping compact weights in isolated execution kernels is striking. On 300 research-level problems drawn from TCS-Bench, an unassisted 27B model initially achieved a meager pass rate of 4.0%. Wrapping the same 27B model in a verification runtime increased the volume of passing proofs by nearly 6x. Beyond simple answer matching, 18% of the generated proofs reached publication-grade quality without fine-tuning a single model weight. All of these verification runs executed entirely on local consumer hardware rather than massive distributed clusters.

In absolute numbers, over 85 of the certified passes generated by the supervisory system reached the publication-ready Grade A standard. By pairing a 27B model with symbolic solvers, researchers unlocked reasoning capabilities that previously seemed restricted to frontier commercial models. The feedback loop transforms the model from a fallible text predictor into a directed proof assistant.

Structural Limits and Memory Failure Modes

Despite the impressive gains achieved by sandboxed execution, programmatic feedback does not solve all reasoning bottlenecks. Integrating an experience loop can allow an agent to discover hidden mathematical laws with interaction terms that a baseline agent without learning fails to identify. In structured environments with consistent rules, historical reflection helps the agent adjust search paths and isolate underlying principles.

However, experimental evidence indicates that memory mechanisms provide no advantage on task sets that lack shared transferable structure. When evaluated on problems with unrelated mathematical domains, accumulated memories produce no performance improvement, and the agent records nothing. Stateful memory layers cannot substitute for analytical structure; they only assist when successive problems exhibit shared formal patterns. Without structural overlap across problems, execution sandboxes must rely strictly on real-time symbolic checking rather than accumulated historical context.

Practical Guidelines for Building Verification Runtimes

Engineers seeking to implement local verification for mathematical tasks can extract several practical design choices from these benchmark findings. Isolate code execution into distinct environments to prevent state corruption. Provide the solving model with a persistent scratchpad for iterative drafting, but force the verification auditor to run inside an ephemeral sandbox. Enforce an unyielding 15-second execution limit on all validation checks to eliminate hanging threads. Configure mpmath to maintain 50 decimal places of precision throughout algebraic transformations. This single configuration prevents floating-point inaccuracies from compromising multi-step proofs. Enforce a hard iteration cap of 200,000 steps using guarded ranges. Halting brute-force loops forces the model to synthesize exact analytical formulas and generating functions.

The next immediate step for practitioners is to benchmark a compact 27B model on TCS-Bench with and without an isolated Python kernel to measure the exact accuracy leap on their local hardware.

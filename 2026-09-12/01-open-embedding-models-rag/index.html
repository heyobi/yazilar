The Retrieval Transition: Standardizing Production RAG on Open Embeddings

Enterprise search architectures are replacing proprietary API endpoints with open-weight models to control index lifecycles and reduce compute overhead.

The Cost of the Default Vector Stack

A benchmark dataset of 20,000 document records with HNSW vector indexing and TOAST storage occupies approximately 170 MB before a single document update occurs.

Most software teams build their initial retrieval-augmented generation systems with commercial embedding APIs. The initial developer workflow appears straightforward. Application code sends text strings over an HTTPS connection, receives dense float arrays, and inserts those vectors into a database table. This architecture functions smoothly until the cloud service provider decides to change its product catalog.

Cloud service providers eventually deprecate and remove older embedding models, forcing systems that rely on them to update their stored embeddings. When an API provider retires an active endpoint, client applications cannot simply redirect traffic to a newer model. Vector embeddings generated by different model architectures inhabit distinct dimensional spaces. You cannot calculate cosine similarity between a query vector from a new model and stored document vectors created by a retired model.

Migrating a vector database from Google text-embedding-004 to gemini-embedding-2 requires rewriting every vector embedding across the document collection. For an enterprise with vast document collections, this requirement triggers an intense maintenance cycle. The engineering team must read every stored document, run inference across the entire archive, and overwrite every table row. Index churn of this scale introduces write amplification, locks database tables, and consumes engineering time.

Database Bloat and Index Churn

Understanding why model deprecation causes severe friction requires examining what happens on disk. Housing vectors directly within PostgreSQL co-locates embeddings, metadata, filters, and relational data without needing separate vector database synchronization pipelines. This co-location simplifies data management for production software. Application tables manage relational attributes while vector columns support nearest-neighbor retrieval in the same transaction.

However, relational database engines handle updates by writing new row versions. When forced model deprecation occurs, updating every vector row triggers intense table bloat. In a benchmark setup, 20,000 document records with HNSW vector indexing and TOAST storage occupy approximately 170 MB of disk space before modifications. Rewriting those 20,000 records leaves obsolete row versions on disk, inflating table footprints and degrading index cache efficiency. Cleaning up this bloat requires vacuum operations that consume disk I/O and processor cycles.

Deploying open models such as EmbeddingGemma on self-managed infrastructure provides greater lifecycle control, though teams may still opt to migrate to newer models for performance gains. When you run open-weight models on your own servers, external deprecation schedules no longer dictate maintenance windows. Engineering organizations choose whether to freeze model weights or update them during scheduled infrastructure overhauls. The stability of self-hosted weights protects production databases from involuntary schema and vector churn.

Quantifying the Turn Toward Open Weights

The operational friction of managed APIs has accelerated the adoption of open-weight embedding models across production systems. Developers are downloading open embedding checkpoints at massive scale from the Hugging Face Hub (Figure 1).

Recent download metrics illustrate the scale of this adoption across the BGE model family (Figure 1). The BAAI/bge-small-en-v1.5 checkpoint recorded 64,607,097 monthly downloads, while BAAI/bge-m3 achieved 37,793,325 downloads (Figure 1). Meanwhile, the BAAI/bge-reranker-v2-m3 model accumulated 18,178,285 downloads, BAAI/bge-large-en-v1.5 reached 12,941,346 downloads, BAAI/bge-base-en-v1.5 logged 10,684,922 downloads, and BAAI/bge-small-zh-v1.5 accounted for 4,949,237 downloads (Figure 1).

These download patterns reveal an engineering priority that public benchmarks often obscure (Figure 1). On public retrieval leaderboards, larger models claim top positions by gaining small fractions of retrieval accuracy. Yet in production deployments, BAAI/bge-small-en-v1.5 commands nearly five times the monthly download volume of BAAI/bge-large-en-v1.5 (Figure 1). This sharp divergence indicates that production engineering teams prioritize lower latency, minimal memory overhead, and fast ingestion over marginal retrieval gains. When an application embeds incoming text streams in real time, small models deliver high throughput on standard compute instances without requiring dedicated GPU clusters. Enterprise teams standardize on compact open weights because they balance practical retrieval quality with operational predictability.

Open Vector Engines Consolidate the Infrastructure

The shift toward self-hosted embeddings coincides with the growth of open vector engines that run directly alongside application services. GitHub stargazer counts reflect developer momentum behind these open storage technologies (Figure 2).

Among dedicated and integrated systems, milvus-io/milvus leads the category with 46,064 GitHub stars (Figure 2). At the same time, qdrant/qdrant maintains 34,504 stars, chroma-core/chroma holds 29,283 stars, and pgvector/pgvector records 22,986 stars (Figure 2). These figures demonstrate that production retrieval infrastructure is consolidating on open-source vector engines (Figure 2).

Teams that prefer operational simplicity frequently deploy pgvector inside PostgreSQL. In this architecture, vectors, metadata, filters, joins, and transactions live beside application rows. Keeping vector data within the primary database avoids the latency and failure modes of synchronizing data across separate systems. Performance benchmarks confirm that integrated relational vector setups meet demanding production requirements. Hardware-tuned PostgreSQL vector setups achieve a p50 latency of 3.5 ms at 0.90+ recall@10 while delivering approximately 4,465 QPS under EXPLAIN ANALYZE testing. A query latency of 3.5 ms eliminates the round-trip overhead of external model APIs, enabling responsive search experiences without remote network dependencies.

Client-Side Embedding Execution

Open-weight models also unlock architectures that proprietary APIs cannot support. An 8-bit quantized BGE-M3 embedding model implemented with Transformers JS and ONNX Runtime Web has a compact memory footprint of 570MB. Quantized open-weight BGE-M3 models can execute directly inside web browsers to deliver multilingual similarity matching with complete data privacy, though memory constraints limit mobile use. Client-side embedding execution eliminates external network requests and prevents sending user data to third-party model APIs.

When a browser processes documents locally, confidential data never leaves the user device. This architecture removes recurring API expenses for the application operator while delivering strict privacy for the end user. For enterprise environments with strict regulatory compliance rules, running open embeddings on the client device resolves data residency challenges.

Operational and Regulatory Trade-Offs

Deploying open models on internal infrastructure introduces distinct challenges that engineering organizations must manage. In March 2025, the U.S. Commerce Department placed BGE developer BAAI on the Entity List, introducing regulatory complications for enterprises deploying its open models. Enterprise legal departments must review open-weight licensing and regulatory designations before approving software components for production use. Additionally, self-hosting requires teams to manage GPU memory allocation, model serving instances, and throughput scaling.

Deploying open models such as EmbeddingGemma on self-managed infrastructure provides greater lifecycle control, though teams may still opt to migrate to newer models for performance gains. When a new architecture offers substantial retrieval improvements, internal teams still face the burden of re-indexing their vector collections. The critical difference is that open models let you schedule that migration on your own terms rather than rushing to beat an external provider deprecation date.

Evaluating Your Retrieval Stack

Before committing to a proprietary embedding API, calculate the true cost of index churn across your document tables. Measure database write amplification by running a complete vector re-indexing test on a staging table. If updating stored embeddings causes unacceptable database bloat or risks downtime, consider self-hosting an open model. Pin a verified open-weight model on your own servers, verify query latencies with local indexing benchmarks, and protect your vector database from forced external migrations.

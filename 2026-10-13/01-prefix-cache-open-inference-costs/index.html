The Prefix Cache Engine: How Radix Trees Halved Open Inference Latency

How open-source radix-tree prefix caching turns multi-turn prefill computation into sub-second memory lookups.

The Multi-Turn Latency Wall in Production

When Asana restructured its browser agent workflows, test execution ran 76x cheaper and 5x faster by eliminating redundant prompt computation. Using GPT-6 Astra in Codex, the engineering team lowered operational overhead while running capable model checkpoints in production tests. Managed cloud providers frequently describe prompt caching as a pricing incentive: OpenAI reported that per-call model cost dropped by about 3x because 89% of the input was served from cache at 5% of the uncached rate.

Yet focusing on cloud billing obscures the technical reality of self-hosted serving infrastructure. For engineering teams managing dedicated hardware, financial billing discounts do not exist. Instead, computing cost and throughput are dictated by the physical memory bandwidth of GPU clusters.

In multi-turn agent environments, time-to-first-token dominates responsiveness. An interactive assistant or autonomous browser agent repeatedly resends conversational history, environment state, and long system instructions on every turn. When an engine recalculates these static token sequences from scratch, prefill latency accumulates. The standard industry reaction of distilling large models into smaller weight configurations often degrades reasoning performance on complex tasks. Optimizing key-value cache reuse addresses this challenge without modifying model weights or output distributions.

The Mechanics of Key-Value State Reuse

Autoregressive transformer inference operates in distinct prefill and decoding stages. During prefill, the engine processes all prompt tokens in parallel to generate key-value tensors across attention layers. During decoding, the engine generates tokens sequentially, reading stored key-value vectors from memory. When consecutive requests share an identical prompt prefix, recomputing those key-value vectors wastes compute cycles.

Prefix caching stores precomputed key-value blocks in memory to eliminate redundant prompt evaluations during inference. This technique differs from traditional response caching because it does not require reusing the final generated answer. The model retains full sampling diversity during generation while bypassing the computational cost of the prompt prefix.

The structure of the prompt determines the success of this mechanism. Arranging static context at the beginning of the prompt and placing dynamic variables such as session identifiers and timestamps toward the end maximizes cache hit rates across subsequent requests. When static system instructions remain anchored at the start, the inference engine reuses identical key-value states across diverse sessions.

External storage layers can extend this architecture across memory tiers. An external key-value storage engine can write attention states once and retrieve them in milliseconds from host RAM or disk, bypassing prefill recomputation for long, recurring prompts. EdgeSync captures the engine cache state after prefix prefill and restores it during subsequent requests sharing that prefix. On an Android phone, restoring local key-value state achieved a 9.9x reduction in time-to-first-token on cache hits with output identical to the uncached path.

Architectural Implementations: Hash Tables Versus Radix Trees

The open serving ecosystem has mobilized around key-value cache runtime optimization, as demonstrated by developer traction across open repositories (Figure 1).

According to GitHub API tracking, vLLM leads high-throughput serving runtimes with 93,679 stars, while SGLang has reached 37,053 stars (Figure 1). In contrast, Text Generation Inference maintains 10,880 stars, and Ollama holds 182,939 stars by focusing on single-user local model execution (Figure 1). The concentration of developer activity around vLLM and SGLang reflects an industry focus on memory management and high-concurrency prefix reuse (Figure 1).

Both leading frameworks take distinct technical approaches to prefix caching. Rather than using a tree representation, vLLM implements prefix caching using a hash-based block mechanism. Under this design, the engine splits prompts into fixed token blocks, computes a hash for each block, and maps hashes to physical memory addresses in a global hash table.

In contrast, SGLang employs a radix-tree data structure to maintain prefix relationships. A radix tree represents token sequences hierarchically, where nodes store token substrings and edges represent shared paths. This structure mirrors the branching patterns of multi-turn dialogues and tree-search decoding algorithms, enabling fast prefix lookups without requiring fixed block boundaries.

In multi-agent settings, system prompts, tool schemas, and historical interaction contexts routinely consume long token sequences (Figure 2).

When shared prefix length scales toward 32k tokens, the architectural divergence between hash-based chunking and radix-tree traversal directly shapes time-to-first-token latency curves (Figure 2). In hash-based block allocation, the engine evaluates token sequences in discrete chunks. If a prompt change alters an intermediate token, all subsequent block hashes change, preventing cache reuse beyond the modification point. As sequences approach 32k tokens, managing hundreds of discrete block lookups introduces memory tracking overhead.

SGLang’s radix tree organizes the shared 32k prefix as a continuous branch in memory. When an incoming request shares that prefix, the engine traverses the tree directly to the corresponding key-value cache pointers. Uncached prefill latency climbs sharply as prompt length grows toward 32k tokens, but radix-tree cache hits flatten time-to-first-token into a near-constant millisecond response (Figure 2). This sub-second initial token latency unlocks real-time multi-agent interactions that would otherwise stall under standard quadratic attention computation.

Operational Tradeoffs and Cache Eviction

Prefix caching does not solve every operational problem. When client applications place dynamic identifiers, timestamps, or random seeds at the beginning of prompt strings, cache reuse drops to zero. In these scenarios, the engine incurs caching lookup overhead without reaping any latency reduction.

Furthermore, preserving key-value cache blocks across requests consumes high-bandwidth memory that would otherwise support larger batch sizes. If multiple concurrent users submit requests with disparate prefixes, the engine experiences cache thrashing: newly written cache blocks evict older blocks before those blocks can be reused. Under heavy concurrency, aggressive eviction policies can reduce cache hit rates and cause latency spikes across active worker nodes.

Structuring Production Workflows

Engineering teams deploying open-source inference runtimes should adopt specific operational practices to maximize key-value reuse.

  • Standardize prompt templates so that all static system messages and tool definitions reside at the beginning of the prompt string.
  • Route incoming requests to inference workers based on prefix affinity to ensure that requests sharing identical prefixes target the same GPU worker nodes.
  • Monitor cache hit ratios alongside GPU memory utilization to prevent cache thrashing during peak traffic periods.

Prefix caching transforms long-context multi-turn serving from an expensive compute problem into an efficient memory lookup operation.
